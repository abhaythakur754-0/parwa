    37→## 1. What Jarvis IS and IS NOT
    38→
    39→### Jarvis IS:
    40→- **A System-State-Aware Operating System** — Always knows current operational mode (Shadow, Supervised, Graduated)
    41→- **A proactive healer** — Detects API failures/DDOS attacks and fixes them automatically
    42→- **A behavioral controller** — Executes commands that change AI behavior via natural language
    43→- **A trust-building explainer** — Shows reasoning, GSD state, and safety mechanisms transparently
    44→- **A GSD Terminal Window** — Displays structured state execution steps in real time
    45→- **A quality coach** — QA reports, training suggestions, health scores
    46→- **A success coach** — Guides clients through onboarding milestones
    47→
    48→### Jarvis IS NOT:
    49→- A generic FAQ bot that answers scripted questions
    50→- A help desk agent that handles customer queries directly
    51→- A sales assistant that promotes products
    52→- An upgrade/payment handler (variants do that)
    53→
    54→### Core Interaction Loop (Every Jarvis Request):
    55→```
    56→1. Intent Classification  (~200 tokens, 1 LLM call) — What does the human want?
    57→2. DB Operation           (0 tokens, pure SQL)          — Execute exact query
    58→3. Response Formatting    (~300 tokens, 1 LLM call)    — Format result for human
    59→─────────────────────────────────────────────────────────────────
    60→Total: ~500 tokens per interaction
    61→```

   110→## 3. Architecture: How Jarvis Talks to Everything
   111→
   112→### 3.1 The Bidirectional Architecture
   113→
   114→```
   115→┌─────────────────────────────────────────────────────────────┐
   116→│                    HUMAN MANAGER                            │
   117→│           (Next.js Jarvis Dashboard / Chat)                 │
   118→└──────────────────────┬──────────────────────────────────────┘
   119→                       │ Natural Language
   120→                       ▼
   121→┌──────────────────────────────────────────────────────────────┐
   122→│                    JARVIS ENGINE                             │
   123→│                                                              │
   124→│  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐ │
   125→│  │ COMMAND  │──▶│  INTENT  │──▶│   DB     │──▶│ RESPONSE │ │
   126→│  │ INPUT    │   │ CLASSIFY │   │ EXECUTE  │   │ FORMAT   │ │
   127→│  └──────────┘   └──────────┘   └──────────┘   └──────────┘ │
   128→│       │              │               │               │       │
   129→│       │              │               │               │       │
   130→│  ┌────┴──────────────┴───────────────┴───────────────┴────┐  │
   131→│  │               SUPABASE (PostgreSQL + pgvector)         │  │
   132→│  │                                                        │  │
   133→│  │  notifications  │  agent_configs  │  system_flags     │  │
   134→│  │  tickets        │  quality_scores │  audit_trail      │  │
   135→│  │  feature_flags  │  client_skills  │  training_data    │  │
   136→│  │  client_legal   │  provision_logs │  batch_queue      │  │
   137→│  └────────────────────────┬───────────────────────────────┘  │
   138→│                           │                                  │
   139→│                    WRITE FLAGS / READ STATE                   │
   140→│                           │                                  │
   141→└───────────────────────────┼──────────────────────────────────┘
   142→                            │
   143→                            ▼
   144→┌──────────────────────────────────────────────────────────────┐
   145→│                 PARWA PIPELINE (Variants)                     │
   146→│                                                              │
   147→│  Node 2 (Smart Route) reads system_flags BEFORE routing      │
   148→│  Node 5 (Act+Verify) checks approval_gates BEFORE executing  │
   149→│  Node 6 (Quality) writes quality_scores AFTER scoring         │
   150→│  Node 8 (Super Node) reads guidance FROM Jarvis               │
   151→│                                                              │
   152→│  PARWA writes to: tickets, conversations, quality_scores      │
   153→│  Jarvis reads from: tickets, quality_scores, conversations    │
   154→│  Jarvis writes to: system_flags, agent_configs, notifications │
   155→└──────────────────────────────────────────────────────────────┘
   156→```
   157→
   158→### 3.2 Communication Mechanism
   159→
   160→Jarvis does NOT call PARWA functions directly. Communication is **bidirectional via shared Supabase tables**:
   161→
   162→**Jarvis → PARWA (Commands):**
   163→- Jarvis writes to `system_flags` table (e.g., `flag_type: "pause_refunds", value: true`)
   164→- PARWA Node 2 reads `system_flags` at the START of every ticket before routing
   165→- If a flag matches the current ticket type → PARWA obeys the flag
   166→
   167→**PARWA → Jarvis (Awareness):**
   168→- PARWA writes to `tickets`, `quality_scores`, `conversations` tables
   169→- Jarvis queries these tables on-demand when the admin asks or on poll cycle
   170→- Jarvis does NOT bulk-load — it runs exact SQL for what's needed
   171→
   172→### 3.3 The 3-Step Loop (Smart Data Access)
   173→
   174→```
   175→Human: "Jarvis, show me today's errors"
   176→
   177→Step 1 — INTENT CLASSIFY (~200 tokens, 1 LLM call)
   178→  LLM receives: "show me today's errors"
   179→  LLM outputs: {
   180→    "intent": "query_errors",
   181→    "time_range": "today",
   182→    "sql_needed": true,
   183→    "sql_template": "SELECT error_type, COUNT(*), MAX(occurred_at) 
   184→                     FROM error_logs 
   185→                     WHERE tenant_id=$1 AND occurred_at >= CURRENT_DATE
   186→                     GROUP BY error_type ORDER BY count DESC"
   187→  }
   188→
   189→Step 2 — DB EXECUTE (0 tokens, pure SQL)
   190→  Supabase executes: the exact SQL above
   191→  Returns: [{error_type: "api_timeout", count: 3, ...}, ...]
   192→
   193→Step 3 — RESPONSE FORMAT (~300 tokens, 1 LLM call)
   194→  LLM receives: the SQL result + human context
   195→  LLM outputs: "You've had 3 API timeouts today, all between 2-4 PM.
   196→               The last one was at 3:47 PM. This correlates with your
   197→               peak traffic window. Want me to increase the timeout limit?"
   198→```
   199→
   200→**Cost: ~500 tokens total per interaction.** Compare to bulk-loading everything (~50,000 tokens).

   210→### Wave 1: Foundation — Database, Auth, Command Parser
   211→
   212→**Goal**: Replace all in-memory mocks with real Supabase. Establish the command infrastructure that every subsequent wave builds on.
   213→
   214→**What Gets Built**:
   215→
   216→#### 1A. Supabase Database Schema
   217→Create ALL Jarvis tables in Supabase (see Section 5 for full schema):
   218→- `notifications` — Replace in-memory notification_center.py
   219→- `system_flags` — Global and per-tenant flags that PARWA reads
   220→- `audit_trail` — Immutable log of every Jarvis action
   221→- `quality_alerts` — Quality degradation alerts
   222→- `quality_scores` — Per-ticket quality metrics
   223→- `training_suggestions` — AI-generated improvement suggestions
   224→- `agent_configs` — Virtual agent configurations
   225→- `client_skills` — Custom skills taught via chat
   226→- `feature_flags` — Per-client feature toggles
   227→- `client_legal_config` — SLA, GDPR, compliance settings
   228→- `agent_provisioning_logs` — Agent creation history
   229→
   230→#### 1B. Supabase Connection Layer
   231→- `jarvis_db.py` — Connection pool (pool_size=20, max_overflow=10, pool_pre_ping=True)
   232→- Row-Level Security (RLS) policies on every table
   233→- Tenant isolation: every query filtered by `tenant_id`
   234→- Connection via Supabase pooler URL (port 6543)
   235→
   236→#### 1C. Natural Language Command Parser
   237→Replace keyword matching with real intent classification:
   238→```
   239→Input: "Jarvis, pause all refund processing"
   240→Output: {
   241→  "intent": "control_pause",
   242→  "target": "refund_processing",
   243→  "scope": "all",
   244→  "confidence": 0.97
   245→}
   246→```
   247→Supported intent families (expandable):
   248→- `query_*` — Information requests (errors, tickets, quality, quota, status)
   249→- `control_pause` / `control_resume` — Pause/resume capabilities
   250→- `control_route` — Redirect channels/capabilities
   251→- `control_mode` — Change system mode (Shadow/Supervised/Graduated)
   252→- `approve_*` / `reject_*` — Batch or individual approvals
   253→- `create_agent` — Provision new virtual agents
   254→- `teach_skill` — Dynamic instruction workflow
   255→- `emergency_*` — Recall, void, shutdown
   256→- `explain_*` — Why did X happen? (GSD state display)
   257→
   258→#### 1D. Auth Integration
   259→- Google OAuth → identify user role (ADMIN, OWNER, SUPERVISOR, TEAM_MEMBER)
   260→- Role-based access control for command authorization
   261→- Admin-only commands: emergency shutdown, agent provisioning, global pause
   262→- All commands logged to `audit_trail`
   263→
   264→#### 1E. Migrate notification_center.py
   265→- Replace `_store: Dict` with Supabase INSERT/SELECT
   266→- Replace `_batch_buffer: Dict` with `batch_queue` table
   267→- Keep the same API (create_notification, get_notification, resolve_notification)
   268→- 30-day retention (GDPR), then archive/anonymize
   269→
   270→**Deliverables**:
   271→- All 11 DB tables created in Supabase with RLS
   272→- `jarvis_db.py` connection module
   273→- `command_parser.py` — intent classification with 10+ intent families
   274→- Migrated `notification_center.py` → Supabase-backed
   275→- Auth middleware for Jarvis API routes
   276→- Tests: DB connection, RLS enforcement, command parsing
   277→
   278→**Effort**: 3-4 days
   279→
   280→**Dependencies**: Supabase project already exists. Google OAuth already configured.

   284→### Wave 2: Awareness Engine — Real Monitoring
   285→
   286→**Goal**: Jarvis actually sees what's happening. Every signal collector in SENSE node becomes real.
   287→
   288→**What Gets Built**:
   289→
   290→#### 2A. Real Stuck Ticket Detection
   291→- Query `tickets` table: `WHERE status = 'pending_approval' AND created_at < NOW() - INTERVAL '12 hours'`
   292→- Escalation tiers: 12h soft reminder, 24h backup alert, 48h critical
   293→- Per-ticket: show quality_score, loop_count, error history, GSD state steps
   294→
   295→#### 2B. Real Integration Health (UCB Monitoring)
   296→- Replace hardcoded `{"sendgrid": "healthy"}` with actual health checks
   297→- For each connected integration (Shopify, Stripe, HubSpot, email, SMS):
   298→  - Store last successful ping timestamp
   299→  - Store last error + response code
   300→  - Calculate uptime percentage
   301→- Webhook health: detect malformed data, track delivery success rate
   302→- Self-healing: auto-restart failed connections (for retries, not permanent fixes)
   303→
   304→#### 2C. Real Quota Monitoring
   305→- Query `agent_configs` + usage tables for actual quota burn
   306→- Per-variant: remaining/total/used/burn_pct
   307→- Trend: compare today's burn rate vs yesterday's vs 7-day average
   308→- Alert when >60% used (warning), >80% (critical)
   309→
   310→#### 2D. Real Accuracy/Drift Detection
   311→- Query `quality_scores` table for recent tickets
   312→- Calculate 7-day rolling accuracy, confidence trend
   313→- Drift triggers: accuracy drops >5% for 3+ days, CSAT drops >0.3, same error 3+ times
   314→- Store drift status in `quality_alerts`
   315→
   316→#### 2E. Real Ticket Flow Metrics
   317→- Query `conversations` + `technique_log` for node-by-node flow
   318→- Show: which nodes each ticket reached, where it got stuck, LLM call count
   319→- Aggregate: "Today 450 tickets: 380 auto-resolved, 50 batched, 20 escalated"
   320→
   321→#### 2F. LLM Cost Tracking
   322→- Already partially exists in `llm_client.py` stats
   323→- Store per-tenant LLM costs in DB: tokens used, model used, cost estimate
   324→- Daily/weekly cost aggregation
   325→
   326→#### 2G. Load Balancing Awareness
   327→- Detect when a variant is at max concurrent capacity
   328→- VIP overflow alert: if VIP customer arrives and all agents busy → alert manager
   329→- Bottleneck detection: "PARWA High handling 5/5 concurrent calls"
   330→
   331→**Deliverables**:
   332→- All 7 SENSE collectors connected to real Supabase data
   333→- Integration health checker with auto-ping
   334→- Drift detection with configurable thresholds
   335→- Stuck ticket cron job (hourly check)
   336→- Cost tracking in DB
   337→
   338→**Effort**: 3-4 days
   339→
   340→**Dependencies**: Wave 1 (DB tables must exist)

   344→### Wave 3: Control System — Commands That Change Behavior
   345→
   346→**Goal**: When the admin says "pause refunds", it ACTUALLY happens. Jarvis writes flags that PARWA obeys.
   347→
   348→**What Gets Built**:
   349→
   350→#### 3A. System Flags Engine
   351→The core of Jarvis control. A `system_flags` table that PARWA reads:
   352→```sql
   353→-- Example flags Jarvis writes:
   354→INSERT INTO system_flags (tenant_id, flag_type, flag_value, scope, set_by, reason)
   355→VALUES ('tenant_123', 'pause_action', 'refund', 'global', 'admin@example.com', 'Jarvis, pause all refund processing');
   356→```
   357→
   358→Flag types:
   359→- `pause_action` — Pause specific action types (refund, returns, account_changes)
   360→- `resume_action` — Resume paused actions
   361→- `redirect_channel` — Route channel to AI or human (e.g., "Handle all Instagram DMs today, I'll take calls")
   362→- `force_mode` — Change system mode (Shadow → Supervised → Graduated)
   363→- `approval_override` — "Always auto-approve this type" (creates permanent approval rule)
   364→- `disable_rule` — "Jarvis, undo my last rule" / "disable my last rule"
   365→- `variant_assignment` — Move skills between variants
   366→- `global_shutdown` — Emergency: kill all AI activity
   367→
   368→#### 3B. Command Execution Engine
   369→For each control command:
   370→1. Parse intent (Wave 1)
   371→2. Authorize (check role from Wave 1D)
   372→3. Validate (is this action legal? budget? plan limits?)
   373→4. Execute (write to `system_flags` + `audit_trail`)
   374→5. Confirm (format response to admin)
   375→
   376→#### 3C. Real-Time Policy Updates
   377→When admin clicks "Always Auto-Approve This Type":
   378→- Jarvis writes to `system_flags`: `{flag_type: "approval_override", flag_value: "address_change", scope: "permanent"}`
   379→- PARWA Node 5 reads this flag BEFORE checking approval gates
   380→- Future address changes skip the approval queue
   381→- Logged in `audit_trail`
   382→
   383→#### 3D. Skill Re-Assignment
   384→"Move Product Recommendations from Mini to PARWA":
   385→- Update `agent_configs` for both variants
   386→- Move associated knowledge base entries
   387→- Notify both variants of config change (via system_flags)
   388→- Verify: test query on new variant
   389→
   390→#### 3E. Emergency Protocols
   391→
   392→**Recall Protocol** (`"Jarvis, recall all emails sent for Free Shipping messages"`):
   393→1. Query `conversations` for matching messages
   394→2. Mark messages as recalled in DB
   395→3. If email provider connected: call Void API (non-financial only)
   396→4. Log to `audit_trail`
   397→
   398→**Void Protocol** (`"Delete pending messages for X"`):
   399→1. Query outbox queue for matching messages
   400→2. Remove from queue (before send, not after)
   401→3. Log action
   402→
   403→**Rage Quit / Emergency Shutdown** (`"Shut everything down"`):
   404→1. Write `global_shutdown` flag
   405→2. PARWA checks flag at Node 1 entry — rejects all new tickets
   406→3. In-flight tickets: allowed to complete current step, then stop
   407→4. Notify all active team members
   408→5. Log to `audit_trail`
   409→
   410→#### 3F. Workflow Redirect
   411→"Handle all Instagram DMs today, I'll take calls":
   412→- Write `redirect_channel` flag: `{channel: "instagram", route_to: "ai"}`
   413→- Write `redirect_channel` flag: `{channel: "calls", route_to: "human"}`
   414→- PARWA Node 2 reads flags → routes accordingly
   415→- Flags can have expiry (e.g., "for today" = set expires_at)
   416→
   417→**Deliverables**:
   418→- `system_flags` table with all flag types
   419→- `command_executor.py` — handles all control commands
   420→- PARWA Node 1 & Node 2 modified to read `system_flags` before processing
   421→- Emergency protocol handlers (recall, void, shutdown)
   422→- Audit trail for every command
   423→- Tests: pause/resume, redirect, emergency, undo
   424→
   425→**Effort**: 4-5 days
   426→
   427→**Dependencies**: Wave 1 (DB + command parser), Wave 2 (awareness of current state before changing it)

   431→### Wave 4: Jarvis-PARWA Bidirectional Channel
   432→
   433→**Goal**: Jarvis and PARWA share state. PARWA asks Jarvis for help. Jarvis gives guidance. Full 2-way communication.
   434→
   435→**What Gets Built**:
   436→
   437→#### 4A. PARWA Reads Jarvis Flags
   438→Modify PARWA pipeline nodes to check `system_flags`:
   439→- **Node 1 (Ingest)**: Check `global_shutdown` flag → reject ticket immediately
   440→- **Node 2 (Route)**: Check `redirect_channel`, `force_mode`, `pause_action` flags
   441→- **Node 5 (Act+Verify)**: Check `approval_override` flags → skip approval for matching types
   442→- **Node 8 (Super Node)**: Check for guidance flags from Jarvis
   443→
   444→Implementation: Add a `load_system_flags(tenant_id)` function called at Node 1 entry, pass flags through state.
   445→
   446→#### 4B. PARWA Asks Jarvis for Help
   447→When PARWA's Super Node (Node 8) can't resolve a ticket:
   448→- Instead of just escalating, write to `jarvis_inbox` table
   449→- Include: ticket_id, stuck_reason, quality_score, what was tried
   450→- Jarvis picks this up on next poll cycle
   451→- Jarvis evaluates: "Can I help with DB data?" or "This needs human attention"
   452→
   453→#### 4C. Jarvis Guidance to PARWA
   454→Jarvis can write guidance that PARWA reads:
   455→```
   456→Jarvis writes to system_flags:
   457→{
   458→  flag_type: "guidance",
   459→  target_ticket: "TKT-882",
   460→  guidance: "Check Shopify order #1234 — customer already received replacement per ticket TKT-850",
   461→  set_by: "jarvis_auto"
   462→}
   463→```
   464→- PARWA Node 3 (Knowledge Fetch) reads guidance flags for the current ticket
   465→- Injects guidance as additional context for reasoning
   466→
   467→#### 4D. Quality Score Write-Back
   468→After PARWA Node 6 scores a ticket:
   469→- Write `quality_scores` row to Supabase
   470→- Jarvis can now query this data for drift detection, reporting, weekly summaries
   471→- Trigger Jarvis evaluation if quality drops below threshold
   472→
   473→#### 4E. Training Data Collection
   474→Every human approval/rejection becomes training data:
   475→- Approved → positive reward signal in `training_data`
   476→- Rejected → negative reward signal
   477→- Human edit of AI draft → both original + corrected stored

   494→### Wave 5: Intelligence Layer — Batching, Confidence, Sentiment
   495→
   496→**Goal**: Jarvis doesn't just pass information — it clusters, scores, and routes intelligently.
   497→
   498→**What Gets Built**:
   499→
   500→#### 5A. Confidence-Based Routing
   501→Every PARWA decision gets a confidence score (0-100%). Jarvis uses this to decide what to show the manager:
   502→
   503→| Confidence | Action | Jarvis Behavior |
   504→|-----------|--------|-----------------|
   505→| **95%+** | AUTO | Log only. No notification. |
   506→| **85-95%** | BATCH | Group similar decisions. One-click approval. |
   507→| **70-84%** | ASK | Show detailed analysis. Manager reviews individually. |
   508→| **<70%** | ESCALATE | Beyond AI capability. Human judgment required. |
   509→
   510→Confidence = weighted average of:
   511→- Pattern match (how closely does this match training data?) — 30%
   512→- Policy alignment (does answer align with uploaded policies?) — 25%
   513→- Risk signals (fraud indicators, VIP customer, high value?) — 25%
   514→- Historical accuracy (has this type been resolved correctly before?) — 20%
   515→
   516→#### 5B. Intelligent Batching (Semantic Clustering)
   517→Replace time-based batching with semantic clustering:
   518→- Group tickets by similarity (not just time window)
   519→- Show: "Batch Request: 5 customers requesting address changes — Confidence: 94-98% — Risk: Low"
   520→- Manager actions: `[Approve Batch]` `[Reject Batch]` `[Review Individually]` `[Shadow This New Type]` `[Automate This Rule]`
   521→
   522→Implementation:
   523→- After PARWA resolves a ticket, store embedding of the ticket + decision
   524→- When batching, compare new tickets against recent batch using pgvector
   525→- If cosine similarity > 0.85 → same batch
   526→
   527→#### 5C. Sentiment Routing (Empathy Engine)
   528→Route customers based on emotional state, not just logic:
   529→- **Angry/Frustrated** (sentiment score < 0.3): Route directly to human manager. Alert: `[!] Angry Customer: Ticket #882`
   530→- **Happy/Neutral** (sentiment score > 0.6): Handle by AI autonomously (often Light Tier for speed/cost)
   531→- **Mixed/Uncertain** (0.3-0.6): Handle by AI but flag for manager review
   532→
   533→Sentiment analysis happens in PARWA Node 1 (already has classification). The sentiment score flows through state. Jarvis reads it and applies routing rules.
   534→
   535→#### 5D. Approval Gates
   536→Hard-coded safety rules that CANNOT be overridden by AI:
   537→- **Always require approval for**: Refunds (any amount), Returns, Account changes, Policy exceptions, VIP customer actions, Financial transactions (credits, adjustments, discounts >$10)
   538→- Approval gates live in `approval_gates` config (DB, not code)
   539→- Even "Always Auto-Approve" has a blacklist: refunds and account changes ALWAYS need approval regardless
   540→- State is preserved during approval wait — ticket doesn't get lost
   541→
   542→#### 5E. Variant Recommendation
   543→When a task seems too complex for current variant:
   544→- Jarvis analyzes: "This requires Shopify API calls + refund logic + cross-reference 3 orders"
   545→- Recommends: "This task needs PARWA High. Your current Mini variant can't handle multi-API calls. Want to upgrade?"
   546→- Checks: is the variant available? Is there budget? What's the queue depth?
   547→
   548→**Deliverables**:
   549→- Confidence scoring formula implemented in PARWA Node 6
   550→- Semantic batching with pgvector similarity
   551→- Sentiment routing rules in PARWA Node 2 + Jarvis
   552→- Approval gates configuration in DB
   553→- Variant recommendation logic
   554→- Tests: confidence routing, batch approval, sentiment escalation
   555→
   556→**Effort**: 4-5 days
   557→
   558→**Dependencies**: Wave 4 (PARWA writes quality scores), Wave 1 (pgvector)

  1152→## 7. LLM Cost Model Per Interaction
  1153→
  1154→### 7.1 Standard Jarvis Interaction (Query)
  1155→```
  1156→Intent Classification:  ~200 tokens in, ~50 tokens out  = ~250 tokens (1 call)
  1157→DB Operation:           0 tokens (pure SQL)
  1158→Response Formatting:    ~300 tokens in, ~150 tokens out = ~450 tokens (1 call)
  1159→────────────────────────────────────────────────────────────────────
  1160→Total per interaction:  ~700 tokens, 2 LLM calls
  1161→Cost (Light tier):      ~$0.0001 per interaction
  1162→```
  1163→
  1164→### 7.2 Control Command (Pause/Resume/Route)
  1165→```
  1166→Intent Classification:  ~200 tokens in, ~50 tokens out  = ~250 tokens (1 call)
  1167→DB Write:               0 tokens (pure SQL)
  1168→Confirmation:           ~100 tokens in, ~50 tokens out  = ~150 tokens (1 call)
  1169→────────────────────────────────────────────────────────────────────
  1170→Total per command:      ~400 tokens, 2 LLM calls
  1171→```
  1172→
  1173→### 7.3 Complex Evaluation (CLARA + Reflexion)
  1174→```
  1175→Signal Collection:      0 tokens (pure DB queries)
  1176→CLARA Clarification:    ~300 tokens in, ~80 tokens out  = ~380 tokens (1 call)
  1177→Reflexion Check:        ~400 tokens in, ~150 tokens out = ~550 tokens (1 call)
  1178→Notification Format:    ~200 tokens in, ~100 tokens out = ~300 tokens (1 call)
  1179→────────────────────────────────────────────────────────────────────
  1180→Total per evaluation:   ~1,230 tokens, 3 LLM calls
  1181→This only runs on poll cycle, not per-chat.
  1182→```
  1183→
  1184→### 7.4 Weekly Report Generation
  1185→```
  1186→Data Aggregation:       0 tokens (SQL)
  1187→Report Generation:      ~2,000 tokens in, ~800 tokens out = ~2,800 tokens (1 call)
  1188→────────────────────────────────────────────────────────────────────
  1189→Total per week:         ~2,800 tokens, 1 LLM call (runs once per week)
  1190→```
  1191→
  1192→### 7.5 Monthly Cost Estimate (per tenant, moderate usage)
  1193→```
  1194→50 chat queries/day × 30 days = 1,500 interactions × 700 tokens = 1,050,000 tokens
  1195→10 control commands/day × 30 = 300 × 400 = 120,000 tokens
  1196→4 poll evaluations/day × 30 = 120 × 1,230 = 147,600 tokens
  1197→4 weekly reports × 2,800 = 11,200 tokens
  1198→────────────────────────────────────────────────────────────────────
  1199→Total: ~1,328,800 tokens/month = ~1.3M tokens
  1200→Cost (Light tier, Groq Llama): ~$0.13/month
  1201→Cost (Mid tier, Gemini Flash): ~$0.66/month
  1202→```
  1203→
  1204→Jarvis is CHEAP to run. The smart query pattern keeps costs near-zero.
